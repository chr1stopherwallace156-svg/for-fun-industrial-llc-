# Fun Industrial V10.7 — Genuine Qwen-generated math tool request trial

## What is already established

On November 23, 2026, V10.5 used seven new, verified V10 validation
prompts with real local pretrained Qwen3-4B CPU inference. Qwen correctly
identified all seven winning window sets, but supplied complete correct
signed subtraction proofs on only 2/7. A deterministic external bridge
verified all 7/7 answers and recorded five model-proof corrections. This
proved external Python orchestration, not native Qwen function calling.

V10.6 tested a host-authorized math-tool contract with a synthetic JSON
proposal. It passed locally; the operator's result was
  FUN_MATH_V106=HOST_AUTHORIZED_MATH_TOOL_CONTRACT_PASS_NOT_DEPLOYED.
V10.6 did NOT involve model-generated tool calls.

## V10.7 objective

Measure whether the ACTUAL original Qwen3-4B model can produce a
syntactically correct, safely executable JSON request for that
previously verified V10.6 math tool.

    SHA-verified V10 validation (new case, not previously inferred)
                      |
                  trusted host
                e3, e5, e8, source_id
                      |
              isolated CPU-only Qwen
                      |
             RAW generated tool JSON
                      |
          V10.6 exact schema validator
                      |
          source_id and integer match check
                 /              \
              fail              pass
               |                  |
          HOLD / REJECT      V10.4 pure math
          NO DISPATCH        read-only dispatch
                                  |
                      verified answer, model request
                      separately recorded as evidence

Important distinction: This is NOT Qwen using a genuine native MCP
transport or structured function-call protocol. It is **one isolated
llama-completion process generating JSON text**, with an external
Python host accepting/rejecting that text as a proposed tool invocation.

## Validation design and provenance

The V10 source has 84 validation samples, 12 per each of seven
winner-set patterns {3}, {5}, {8}, {3,5}, {3,8}, {5,8}, {3,5,8}.
V10.1 used the first 2/pattern: 14 prior examples.
V10.5 used the next 1/pattern: seven more examples.

V10.7 requires:
- authentic, SHA-matched V10 training/validation source and ground truth;
- unchanged prior V10.1 and V10.5 reports, with matching model identity
  and saved inference text fingerprints;
- all 21 previously used validation cases excluded;
- selects the next 1 unused example per pattern: seven NEW cases;
- mathematical oracle labels independently checked;
- never opens the reserved V10 84-example final test set.

This is a small engineering measurement, not broad robustness evidence.
Although the chosen problems are previously unseen by the experiment,
they use the same synthetic generation template as V10 training.

## Prompt and execution limits

Qwen sees the validation question, its original three error numbers,
a host-assigned source_id, and instructions to propose ONLY a strict
JSON object in the V10.6 schema:

- schema = fun-math-tool-proposal-v1
- tool = verify_window_math
- source_id = host-assigned source identifier
- arguments = exactly e3, e5 and e8 as JSON integers

The program does not hand the model a completed JSON answer or
synthetic request fixture, so a success represents actual
model-generated JSON under instruction.

The host independently obtains the errors from SHA-verified source data.
The V10.6 contract will reject anything different from those numbers.
Untrusted output never becomes a source of authority, and malformed
requests are never silently repaired into valid tool calls.

Each of seven original-model inference processes is:
- sequential, CPU-only, four threads, no LoRA;
- temperature zero, seed 6427, 160 generated tokens;
- wrapped by the existing V7.1 RAM/commit watchdog and child timeout;
- implemented through the preexisting offline llama-completion.exe;
- excluded from the live FunIndustrial Qwen/dashboard/REA processes.

Any request containing markdown, extra content, multiple JSON objects,
unknown tools, unknown schema versions, duplicate or extra keys,
wrong or noninteger numerical data, missing fields or mismatched
source_id must be rejected without tool dispatch.

## What will count as success

Primary metrics are:
1. total_real_qwen_cpu_requests: seven completed offline model runs;
2. valid_model_generated_requests: number of requests genuinely
   generated by those runs and accepted by the host;
3. invalid_model_generated_requests_rejected: attempted outputs that
   did NOT trigger any math-tool dispatch;
4. trusted_host_dispatches: equal to valid accepted requests;
5. host_tool_correct_results: correct deterministic math outputs
   among actual accepted requests.

The host oracle can independently calculate seven expected answers
for diagnosis even if all seven model requests are rejected.
Those are NOT counted as successful tool calls, and do NOT prove
Qwen can use tools.

The report clearly discloses:
- source SHA fingerprints are identities, NOT cryptographic signatures;
- native_model_tool_call_protocol_proven = false;
- training_performed = false;
- live_fun_or_rea_modified = false.

## Files and preserved state

This experiment adds code and 20 offline test cases to the existing
repository branch. It does not write to, edit or overwrite prior V10,
V10.1, V10.5 or V10.6 data. New reports are written only after
explicit operator approval to a fresh directory:

%LOCALAPPDATA%\FunIndustrial\QwenActualGGUFLoRAV5\math-qwen-real-tool-requests-v107\

Outputs: native Qwen stdout/stderr logs per case, plus
tool-requests-report.json containing raw proposed JSON and
accepted/rejected status. The destination fails closed if it exists.

No model download, training, LoRA deploy, live dashboard route
changes, MCP service registration, external API, emailing, payment,
or Elektron action occurs.

## Run instructions

Read-only preflight, after clean checkout and fast-forward:

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Run-Fun-Qwen-Tool-Requests-V107.ps1

Explicitly approved genuine isolated model-request trial:

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\Run-Fun-Qwen-Tool-Requests-V107.ps1 -Execute -Approval I_APPROVE_ISOLATED_QWEN_V107_TOOL_REQUEST_EXPERIMENT

The PowerShell runner first performs 20 offline safety tests. It
checks the same protected listener ownership before and after
inference. It never restarts/changes those live services.

Expected terminal markers **only if execution succeeds on the PC**:

    FUN_QWEN_V107_OFFLINE_TESTS=PASS
    FUN_QWEN_V107_PREFLIGHT=...
    FUN_QWEN_V107_CASE_RESULT=... [7 lines]
    FUN_QWEN_V107_RESULT=...
    FUN_QWEN_V107=REAL_MODEL_TOOL_REQUESTS_MEASURED_NOT_DEPLOYED
    FUN_QWEN_V107=REAL_MODEL_TOOL_REQUESTS_MEASURED_NOT_DEPLOYED

If a test fails, keep the hold in place and investigate the exact
cause; do not overwrite prior artifacts or skip authorization.

## Next possible milestone after evidence

If V10.7 shows genuine valid model-generated JSON, develop a separate
explicitly approved two-turn simulation: have the host return the
tool response to isolated Qwen and evaluate if the model faithfully
relays the verified values rather than reverting to made-up arithmetic.

Before any live Fun Industrial integration, test prompt injection,
multi-turn trust boundaries, provenance, hostile source documents,
tool-call ambiguity, and operator authorization for every action.
Keep improving neural reasoning separate from tool-assisted results.
